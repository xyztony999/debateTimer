## 第一部分：PRD 正文

### 1. 业务背景与目标（G1）

系统已上线并有外部用户，但服务端对「谁在什么时候登录、谁改了谁的权限、谁动了注册开关」没有任何留痕（D-01 PRD v1.0 §7 的 N4 缺口）。P-04 提供一条只增的安全与账号事件记录，服务两类人：

- 负责人与管理员：发生账号盗用、误操作或纠纷时，能按时间、账号、事件类型回溯安全相关操作；
- 用户本人：能在设置页查看自己账号的登录记录（隐私说明中告知的查阅权）。

本模块按《个人信息保护法》《通用数据保护条例》《个人信息保护与电子文件法》关于目的限定、数据最小化、存储限制、访问控制与个人查阅权的共同要求设计，要求与做法的逐条对照见 R20 §3。本文不作也不暗示任何合规结论。

### 2. 角色与职责（G3）

| 角色 | 职责与权限 |
|------|-----------|
| 系统事件源（非角色） | S-01、D-01、D-02、S-03 的写入点在业务操作成功后或登录尝试结束时调用审计写入器；事件类型只能取自 §3.3 白名单 |
| 管理员 | 在管理后台按事件类型、用户、时间范围筛选并分页查阅全量事件；只读 |
| 注册用户 | 在设置页查看本人登录类事件（§5.5）；只读 |
| 平台机制（非角色） | 留存到期自动删除（TTL 索引）；账号删除时的日志清洗（D-01 触发）；备份恢复后的孤儿清洗 |

访客、计时操作员、大屏观众没有读取入口。不存在任何可以修改或删除单条日志的角色。

### 3. 功能范围（G2）

#### 3.1 做什么

| 功能点 | 说明 |
|--------|------|
| 事件写入 | 单一写入函数 `recordAudit(...)`；事件类型白名单校验；`detail` 按事件类型白名单构造；写入失败则当前请求失败（D64） |
| IP 记录策略 | 按事件情境决定是否记录来源 IP（§5.1）；记录时为完整 IP |
| 留存与自动删除 | 每条事件带 `expireAt = at + 184 天`；TTL 索引到期删除（§5.3） |
| 管理员查阅 | 分页与筛选（事件类型、用户名、时间范围、结果）；用户 id 在读出时解析为用户名 |
| 本人登录记录 | 只返回当前账号为所涉账号的登录类事件；失败事件的 IP 脱敏 |
| 账号删除清洗 | 账号被删除时删除其自身活动事件、匿名化其余引用（§5.4） |
| 备份与恢复 | 纳入备份集合；恢复后对已不存在的账号重放清洗（§5.6） |

#### 3.2 不做什么

- 不记录用户内容：模板文本、阶段配置、队名、署名、比赛记录、广场复制行为一律不记。
- 不记录凭据与秘密：口令（明文或散列）、动态口令、恢复码（明文或哈希）、TOTP 密钥（明文或密文）、会话令牌、预登录凭据。
- 不记录一般浏览与常规内容操作（打开页面、保存自己的模板、删除自己的比赛记录、登出）。
- 不提供修改、删除、清空、导出的接口或界面；日志的删除途径只有留存到期、账号删除清洗、备份恢复清洗三条系统路径。
- 不做防篡改加固（哈希链、只追加存储、异地转发、WORM）。日志与业务数据同库同权限，拥有数据库写权限的人可以改写它。这是已知边界，见 §10。
- 不记录「管理员查阅审计日志」这一行为本身：单一管理员场景下是自指噪声，后续如有要求再补。
- 不记录限流命中（429）事件：会按请求量线性膨胀日志体积，且登录失败事件已覆盖同一攻击面。
- 不做 IP 地理解析，不采集设备指纹或 User-Agent。

#### 3.3 事件目录（EP-AUDIT-01）与逐条必要性

「来源」列标明该事件是否属于用户裁定的最低集合；标「增补」的每一条都给出必要性。`detail` 列是该事件允许写入的全部专属字段，除此之外不得追加。

| # | 事件类型 | 中文名 | 结果 | 操作者 → 所涉账号 | detail（白名单） | 必要性 | 来源 |
|---|---------|-------|------|-------------------|------------------|--------|------|
| 1 | `registered` | 注册成功 | success | 新账号 → 自己 | `role` | 账号诞生的起点；排查垃圾注册与「首个管理员」归属 | 最低集合 |
| 2 | `login_succeeded` | 登录成功 | success | 登录者 → 自己 | — | 判断「哪些登录不是本人」的基本依据 | 最低集合 |
| 3 | `login_failed` | 登录失败 | failure | 匿名（口令未通过）→ 被尝试的账号或无 | `reason`、`attemptedUsername`（仅当无此账号且符合用户名格式） | 暴力破解与撞库的唯一可观测信号；禁用账号的口令泄露只能从这里发现 | 最低集合 |
| 4 | `totp_succeeded` | 二次验证成功 | success | 登录者 → 自己 | — | 证明该次登录经过了第二因子 | 最低集合 |
| 5 | `totp_failed` | 二次验证失败 | failure | 匿名（持预登录凭据）→ 凭据所属账号；绑定确认时口令不匹配为已登录的本人 → 自己 | `method` | 口令已泄露但第二因子未失守的直接证据 | 最低集合 |
| 6 | `totp_bound` | 两步验证绑定 | success | 操作者 → 自己 | `channel`、`rebind`、`recoveryCodeCount` | 第二因子何时生效；意外绑定意味着会话或口令失守 | 最低集合 |
| 7 | `totp_unbound` | 两步验证解绑 | success | 操作者 → 自己 | `channel` | 安全强度下降的时刻 | 最低集合 |
| 8 | `recovery_code_used` | 恢复码使用 | success | 登录者 → 自己 | `remaining` | 验证器丢失后的登录凭据；用尽提示管理员介入 | 最低集合 |
| 9 | `totp_reset` | 两步验证重置 | success | 管理员或服务器脚本 → 目标账号 | `channel` | 增补：移除他人第二因子是高权限动作，不留痕就成了无记录的降级通道 | 增补 |

| 11 | `user_created` | 管理员开号 | success | 管理员 → 新账号 | `role` | 增补：绕过注册开关的账号创建（尤其是直接创建管理员）是提权路径，注册事件只覆盖自助注册 | 增补 |

补充说明：

- #15 `user_deleted` 写入时带被删账号标识，随即被同一次请求内的清洗匿名化（§5.4），因此落库后该行的「所涉账号」为空。
- #17 属主发布后再次保存模板，会使发布标志被抹除并退出广场（S-02 API v1.0 §1.3 注记的既有行为）。该退出路径不产生 `gallery_unpublished` 事件：它是常规保存的副作用而非一次下架操作，且 S-02 保存路径本轮不改。这是已知缺口，列入 R20 §11 待决事项。
- 管理员经 `/settings?ownerId=` 代管编辑他人模板（S-02 保存路径）本轮同样不记事件，理由同上，列入待决事项。

### 4. 领域对象与关系（G4/G5）

| 对象 | 说明 | 与其他对象关系 |
|------|------|---------------|
| 审计事件 | 一条不可变的安全或账号事实：类型、时间、结果、操作者、所涉账号、来源 IP、专属字段 | 引用账号（S-01）与模板（S-02）时只存其 id，不级联修改对方 |

### 5. 业务规则（N3）

#### 5.1 来源 IP 记录策略（先告知后收集）

| 情境 | 是否记录 IP | 依据 |
|------|------------|------|
| 匿名登录失败（口令未通过；「账号不存在」与「口令错误」统一 401 的情形都算） | 记录 | 登录页在表单之前展示隐私说明入口与「记录登录尝试来源 IP」的提示（login PageSpec v1.1 §5.5）；无法逐人取得同意的场景以事前告知覆盖 |
| 二次验证失败（持预登录凭据） | 记录 | 同上，该步骤是登录表单的后续步骤 |
| 已登录或已识别账号的事件，且该账号已同意**当前版本**隐私说明 | 记录 | 同意留痕 `users.privacy.version === 当前版本` |
| 已登录或已识别账号的事件，但该账号尚未确认当前版本（存量用户首次访问之前） | **不记录**，`ip = null` | 用户裁定：已有用户在其确认之前，其审计事件不得记录 IP（R20 D50） |
| 注册成功、隐私说明同意 | 记录 | 同意发生在同一请求内、审计写入之前 |
| 管理员对他人操作 | 取决于**操作者**（管理员）是否已确认当前版本 | IP 是请求发起方的数据 |
| 系统路径（留存删除、脚本重置） | 不记录 | 没有请求来源 |

一个需要知悉的取舍：匿名登录失败时，即使被尝试的用户名对应一个尚未确认隐私说明的存量账号，也按第一行记录来源 IP。理由是此时操作者未经身份验证，事件归属于发起请求的一方而非账号本人，而这类长期不登录的账号恰是口令泄露后最容易被尝试的对象。若负责人希望从严，可改为「被尝试的存量账号尚未确认时不记 IP」，改动集中在策略函数一处（P-04 API §4.1.4 的 `ipFor()`）。

#### 5.2 写入规则

1. 事件类型必须属于 EP-AUDIT-01，否则写入器抛错，误用在开发期即暴露。
2. 写入只走 `insertOne`。代码库内不存在针对 `audit_logs` 的业务性 `updateOne` 或 `deleteMany`；仅有的两处批量处置（§5.4、§5.6）封装在 `auditLog.js` 的两个具名函数中。
3. 审计写入在业务写入之后、响应之前 `await`；写入抛错则当前请求返回 500，不静默放行（D64）。登录成功场景下会话记录已创建但响应为 500，客户端拿不到会话 Cookie，该记录无人持有，随会话 TTL 过期。
4. 一个事实一条事件。启用两步验证的一次登录会产生两条：`totp_succeeded`（第二道验证通过）与 `login_succeeded`（会话建立），因为它们是先后两个事实。幂等重放（PUT 同值、PATCH 未变化字段、重复下架返回 `unpublished:false`）不产生事件。

#### 5.3 留存与自动删除

- 每条事件写入时计算 `expireAt = at + 184 天`。留存期是单一常量（2026-11-24 用户裁决由 180 天改为 184 天，目的是覆盖任何起算点下的六个自然月），调整只改一处；调整只影响之后写入的事件，已写入事件的到期时间不变。
- TTL 索引 `audit_logs.expireAt`（`expireAfterSeconds: 0`）在服务启动时与其他索引一并创建，沿用 `server/index.js` 的 `createIndex` 惯例。
- **生效条件与边界**：
  - TTL 监视线程约每 60 秒运行一次，事件在其到期后的一分钟内被删除，不是到点即删。
  - 服务进程所属的 MongoDB 不运行时不会删除，恢复后下一轮即继续。
  - TTL 只对 BSON Date 类型字段生效，本设计的 `expireAt` 恒为 Date。
  - 固定大小（capped）集合，或以 `ttlMonitorEnabled=false` 启动的实例不执行 TTL。本部署为普通集合、默认参数。
  - 被删除文档占用的磁盘空间由 MongoDB 在后续写入中复用，不立即归还操作系统。

#### 5.4 账号删除时的日志处置

由 D-01 删除用户流程调用，函数 `scrubUserAuditLogs(auditLogs, userId)`：

1. 先写入 `user_deleted` 事件，此时带被删账号标识。
2. **删除**该账号的自身活动事件：`subjectUserId` 为该账号且 `type` 不等于 `user_deleted` 的全部文档（登录、二次验证、绑定、同意，以及别人对这个账号做的角色变更、禁用、重置等）。这些记录离开账号后没有主体，保留只会留下无主的个人数据。
3. **匿名化**其余引用该账号的文档。步骤 2 之后，这些文档只剩两类：被删账号曾作为**操作者**的事件（例如它作为管理员改过别人的角色），以及 `user_deleted` 自身。处置是把指向该账号的标识置空；如果该账号是操作者，`ip` 一并置空，因为那是它的 IP。操作者是别人时，别人和别人的 IP 保留，并写入 `anonymizedAt`。事件类型、时间、结果、`detail` 保留。例如「某管理员在 T 删除了一个账号」「某账号在 T 把某用户设为管理员」仍然成立，只是无法再指向被删账号。
4. 写入 `audit_scrubbed` 事件，记录步骤 2、3 的条数。

**顺序**：清洗在删除账号文档**之前**执行。若清洗成功而后续删除失败，该账号的历史登录记录已清空但账号仍可正常使用，管理员重试删除即可。反之若先删账号再清洗，一旦清洗失败，带标识的日志会永久残留且无法重试。

`detail` 中不存被删账号的用户名；`templateId` 这类非个人标识保留。

#### 5.5 读取规则

- **管理员**：全量，`pageSize` 上限 100；服务端把 `actorUserId` 与 `subjectUserId` 批量解析为用户名，账号已不存在时对应字段为空。IP 为完整值。
- **本人**：强制以当前账号为所涉账号，只返回 `login_succeeded`、`login_failed`、`totp_succeeded`、`totp_failed`、`recovery_code_used` 五类；`pageSize` 上限 50。
- **本人视图的 IP 脱敏**：结果为成功的事件显示完整 IP，因为是本人发起的请求；结果为失败的事件显示脱敏值，因为发起请求的可能是持有口令的第三方，其完整 IP 不应展示给另一名用户。脱敏规则：IPv4 保留前三段（`203.0.113.*`），IPv6 保留前四组（`2001:db8:1234:5678::/64`）。脱敏在读出时计算，不落库。
- 两类读取都不返回 `expireAt`，都不提供按 IP 反查。

#### 5.6 备份与恢复

- `audit_logs` 加入 `server/scripts/backup.js` 的 `COLLECTIONS`。备份文件保留 14 天后轮换删除（既有 `KEEP_DAYS`）。
- 备份中的审计日志含 IP 与账号标识，因此备份副本使这部分数据的实际存续期比 184 天多出至多 14 天，被清洗账号的标识在 14 天内的备份中也仍然存在。这一延伸是有界的，并已在隐私说明的留存期限一节写明。
- **恢复后重放清洗**：`--restore` 完成全部集合回放后调用 `scrubOrphanAuditLogs(db)`，对 `audit_logs` 中引用到、但 `users` 集合里已不存在的账号 id，重跑 §5.4 的步骤 2、3。否则用一份账号删除之前的备份恢复，会让已清洗的标识重新出现。
- `expireAt` 早于当前时间的文档在恢复后由 TTL 下一轮清除。**前提是恢复时日期字段被还原为日期类型**（见下一条）。
- **恢复时还原日期类型**（代码阶段实测发现的缺陷，已修复）：备份文件是文本，`at`、`expireAt` 在其中是 ISO 字符串；MongoDB 的 TTL 索引只按 BSON 日期删除文档，对字符串不做处理。2026-11-24 在 MongoDB 7.0.24 上实测：同一条已过期的事件，`expireAt` 为日期时 65 秒内被删除，为字符串时一直保留——即还原回来的审计日志永远不会过期。因此 `restoreInto()` 对 `audit_logs` 与 `users` 两个集合，把 `at`、`expireAt`、`consentedAt`、`boundAt`、`expiresAt` 还原为日期；修复后实测，还原回来的已过期事件在 35 秒内被删除。其余集合的既有字段都是数值时间戳，不受影响。

### 6. 状态与流转（T2）

审计事件是不可变事实，没有状态机，只有一条生命周期：

```
写入(at, expireAt = at + 184 天) --留存到期(TTL, 约一分钟内)--> 已删除
      └--所属账号被删除--> 自身活动事件: 删除 / 其余引用: 匿名化
```

### 7. 业务字段（T1）

`audit_logs` 集合：

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `_id` | ObjectId | — | 事件 id，响应中字符串化为 `id` |
| `type` | string | EP-AUDIT-01 | 事件类型 |
| `at` | Date | 服务端时钟 | 事件时间，列表排序键（降序） |
| `expireAt` | Date | `at + 184 天` | TTL 字段，不对外返回 |
| `result` | string | EP-AUDIT-02 | 尝试类事件区分 success 与 failure，其余恒为 success |
| `actorUserId` | ObjectId 或 null | — | 操作者；匿名或系统为 null |
| `subjectUserId` | ObjectId 或 null | — | 事件所涉账号；不涉及账号或已匿名化为 null |
| `ip` | string 或 null | 完整 IP；IPv4 映射地址归一为点分形式 | 是否记录按 §5.1 |
| `detail` | object | 只含 §3.3 白名单字段 | 事件专属字段；没有专属字段时为 `{}` |
| `anonymizedAt` | Date | 仅匿名化后的文档存在 | 清洗时间 |

两个 id 字段统一存 ObjectId，可被备份脚本的 `reviveDeep` 往返；用户名在读出时解析，不冗余存储。唯一例外是 `login_failed.detail.attemptedUsername`：它记录的是一个不存在的账号名，没有 id 可存。

### 9. 异常与降级（N2）

| 场景 | 行为 |
|------|------|
| 审计写入失败（数据库不可用等） | 当前请求 500；`console.error` 只带事件类型，不带事件内容 |
| 事件类型不在白名单 | 写入器抛错，请求 500；属编程错误，单测覆盖全部调用点 |
| 用户名解析失败（账号已删除） | 响应中对应字段为 null，不报错 |
| 筛选参数越界 | `pageSize` 超上限按上限处理；`type` 与 `result` 非法值 400；`from` 不小于 `to` 时 400 |
| TTL 删除延迟 | 至多约一分钟，属预期 |

### 10. 非功能性要求（N1）

- **量级**：社团规模。以当前 10 个账号、每账号每天 10 次登录类事件估算，184 天约 18,400 条；登录失败受 P-02 限流约束（每 IP 每 15 分钟 20 次）。单文档约 200–300 字节。
- **查询**：列表按 `at` 降序加可选等值筛选，均有复合索引；`total` 用 `countDocuments`，该量级下可接受。
- **写入**：每个被审计的动作增加一次 `insertOne`，与业务写入同库。
- **已知边界**：日志与业务数据同库，不具备对「持有数据库写权限者」的防篡改能力；进程内存中的限流计数与预登录凭据不落库。后续若需更强的防篡改保证（哈希链、异地转发），在 `recordAudit` 这一个入口上扩展。
- **IP 真实性前提**：`req.ip` 是否为真实客户端地址，取决于「api 域名保持仅 DNS 解析」或「Nginx 配置 Cloudflare realip」二者之一成立，见 R20 §9.3。

### 11. 历史与追溯（N4）

本模块自身就是追溯能力的载体，没有变更历史需求；`audit_scrubbed` 事件是清洗动作的追溯记录。
