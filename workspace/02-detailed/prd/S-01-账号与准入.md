## 第一部分：PRD 正文

### 1. 业务背景与目标（G1）

系统为辩论社提供赛制模板、比赛计时与复盘记录能力，这些资产按账号归属隔离（模板、比赛记录均以 ownerId 存储）。S-01 解决「谁能进入系统」：

- 访客可自行注册账号，无需管理员人工开通；
- 已注册用户以用户名与口令登录，登录态跨页面保持；
- 管理员可开放或关闭公开注册，防止滥用；
- 【R20】登录可在口令之外增加第二道验证（两步验证）：管理员账号必须使用，普通用户自愿；
- 【R20】在使用系统之前向用户说明个人数据的收集与使用方式并取得确认：注册前必须同意，已注册用户再次使用时须确认最新版本。

服务对象：访客（注册、登录）、注册用户与管理员（登录态保持、两步验证、隐私说明确认）、管理员（准入开关、强制绑定两步验证）。

#### 3.2 不做什么

- 不做邮箱或手机号注册、短信或邮件验证码、找回密码、改密自助服务（改密由管理员在用户治理中代操作，属 D-01）。
- 【R20 修订】不做第三方 OAuth 登录，不做硬件密钥（Passkey、WebAuthn）。两步验证自 v1.1 起提供，算法限定为 TOTP（RFC 6238）：不接受基于计数器的 HOTP，也不接受 otpauth 链接里的其他算法或位数参数。
- 不做注册审批流（注册即时生效，无待审状态）。
- 不做用户清单、禁用、角色管理（属 D-01 权限与用户治理；S-01 仅消费 `disabled`、`role` 字段对登录的影响）。
- 不做注册开关之外的系统配置存储（app_settings 单文档模式属 D-02；S-01 只定义 `registration` 单例的读取语义）。
- 【R20】不做用户自助导出或删除个人数据（本轮范围外，见 R20 §10）。
- 【R20】不做隐私说明的后台编辑界面：说明正文随代码发布，版本以常量标识。
- 【R20】不做两步验证密钥（主密钥）的轮换工具；更换主密钥会使已绑定的密钥无法解密，须在上线前妥善保管（R20 §8.2）。

### 5. 业务规则（N3）

#### 5.1 注册开关三参语义（核心规则）

`isRegistrationOpen(userCount, allowRegistration, adminSetting)`（`server/lib/authPolicy.js:11-23`）按优先级判定注册是否开放：

| 优先级 | 条件 | 结果 | 业务含义 |
|--------|------|------|---------|
| 1 | `userCount === 0`（系统无用户） | 恒为开放 | 全新部署绝不能被一份陈旧的「关闭」配置锁死；首个管理员账号不受开关影响 |
| 2 | `adminSetting !== undefined`（管理台已写入） | `Boolean(adminSetting)` | 管理侧持久化值覆盖 env 回落值 |
| 3 | 其他（管理台未设置） | `Boolean(allowRegistration)`（env 回落，默认关闭） | 未设置时与纯 env 行为逐字节兼容 |

补充语义：

- env 解析：`parseAllowRegistration` 仅 `'true'`、`'1'`（大小写不敏感）为真，其余（含未设置）为假（`server/lib/authPolicy.js:6-9`）。
- `/api/auth/status` 与 `/api/auth/register` 共用同一快照函数 `registrationState()`，一次读库同时取用户数与开关，保证「首用户角色判定」与「开关判定」不可能不一致（`server/routes/auth.js:35-54`）。
- 管理台读写接口返回 `source`（`env` 或 `admin`）与 `envDefault`，前端可区分当前生效来源（`server/routes/admin.js:45-63`）。

#### 5.4 限流规则（依赖 P-02，遵奉者模式）

| 端点 | 默认限额（env 可调） | 说明 |
|------|--------------------|------|
| POST /api/auth/login | 每 IP 20 次 / 15 分钟 | 匿名口令校验是暴力破解目标，bcrypt 之外再加刹车 |
| POST /api/auth/register | 每 IP 10 次 / 60 分钟 | 注册关闭期间仍计数（防滥用面） |
| GET /status、POST /logout、GET /me | 不限 | 保证被限流客户端仍能干净退出 |

依据：`server/routes/auth.js:27-33`；`server/lib/rateLimits.js:17-31`；【R20】EP-PROTECT-03。

#### 5.5 【R20】两步验证规则

**算法与绑定方式**

- 标准 TOTP（RFC 6238）：30 秒步长、6 位数字、SHA-1。兼容主流验证器应用。
- 绑定提供三种方式，指向同一个密钥：`otpauth://` 链接（手机上点击直接拉起验证器）、二维码（前端用懒加载的二维码库在本地生成，密钥不发给任何第三方）、手动输入 Base32 密钥（分组显示）。
- 绑定须输入一次动态口令确认，确认通过才算启用。密钥在确认前只是「待确认」状态，10 分钟内未确认自动作废。
- 绑定或重新绑定成功后，该账号在其他设备上的登录会失效（当前设备保留）。已启用的账号若怀疑会话被盗，可以通过重新绑定把别的设备挤下线。

**登录流程**

1. 口令通过后，若账号未启用两步验证，直接建立会话（现有行为）。
2. 若已启用，返回「需要二次验证」与一个**预登录凭据**，此时**没有会话**。凭据 5 分钟有效、只能用一次、服务端只存其散列、不落库（进程内存）。
3. 用户输入 6 位动态口令或一个恢复码。正确则建立会话；预登录凭据随即作废。
4. 凭据过期或尝试次数用尽后，回到口令步骤重新开始。

**启用策略**（用户裁定）

| 账号类型 | 是否必须 | 能否关闭 | 说明 |
|---------|---------|---------|------|
| 管理员 | 必须绑定 | 不能关闭 | 未绑定的管理员登录后进入强制绑定引导，完成前不能访问其他功能；可重新绑定（换手机） |
| 普通用户 | 自愿 | 可以关闭 | 在设置页自行开启、重新绑定、关闭 |

**防暴力破解与重放**

- 尝试限流：每账号 15 分钟内最多 5 次失败，动态口令与恢复码共用这一个计数。第 5 次失败后预登录凭据作废并返回 429（带 Retry-After）。成功后计数清零。计数在进程内存，服务重启清零。绑定确认（TOTP-CONFIRM）的口令不匹配也计入这同一个计数：未达上限返回 401 并带 `data.attemptsRemaining`，达到上限返回 429；确认成功后清零。
- 不可重放：同一个 30 秒时间步的动态口令只能成功一次。为容忍时钟偏差，允许前后各一步的口令，但已经用过的时间步不再接受。判定与「记录已用时间步」是一次原子更新，并发提交同一个口令只有一个成功。
- 恢复码一次性：每枚只能用一次，使用即从账号上移除。

**恢复码**

- 绑定成功时生成 10 个，每个 10 字符，显示为 `XXXXX-XXXXX`（字母表去掉了 0、O、1、I 这类易混字符）。
- 只在绑定成功的那一次响应中展示明文；服务端只存 SHA-256 散列。
- 用一枚少一枚。全部用尽后，普通用户只能请管理员重置，管理员只能走服务器脚本。

**管理两步验证需要密码证明**

- 开启、重新绑定、关闭，都要求「10 分钟内刚用口令登录过」，或在请求中提供当前口令。目的是防止别人借用一台没退出的电脑给账号绑上自己的验证器，或把两步验证关掉。
- 强制绑定引导紧跟在口令登录之后，因此正常不需要再输口令。

**管理员重置与自救通道**

- 管理员可在管理后台重置**其他**账号的两步验证（不能对自己操作，自己换手机走重新绑定）。重置会移除该账号的两步验证并销毁其全部会话；之后该账号登录时，管理员重新进入强制绑定，普通用户回到仅口令登录。
- 线上只有一名管理员。该管理员丢失验证器且恢复码用尽时，没有任何界面能解围，因此提供服务器脚本 `reset-totp.js`：需要服务器命令行权限才能执行，执行后写审计事件。

**密钥保护**

- 密钥以 AES-256-GCM 加密后存库，主密钥来自服务器环境变量 `TOTP_SECRET_KEY`（32 字节的 base64）。加密时把账号 id 绑定进认证数据，密文换到别的账号上无法解密。
- 备份导出里只有密文；主密钥不在备份内。
- **未配置主密钥时**：两步验证整体停用，绝不退回明文存储。具体表现是服务启动日志报错、绑定接口返回 503、管理员后台显示提示；管理员的强制绑定暂不生效，否则管理员会被锁在系统外。已经绑定的账号此时无法通过二次验证，不会退回仅口令登录。
- 更换主密钥会让已绑定的密钥全部无法解密，上线前须妥善保管（R20 §8.2）。

#### 5.6 【R20】隐私告知与同意规则

| 场景 | 做法 |
|------|------|
| 登录页（所有访客） | 表单**之前**展示一行提示与「隐私说明」入口。点击后在弹窗中展示当前版本全文，可切换三种界面语言。入口在表单之前，是为了覆盖「登录失败尝试」这类拿不到逐人同意的情况 |
| 注册 | 必须勾选「我已阅读并同意隐私说明」才能提交；未勾选时提交按钮禁用。进入注册模式时预取说明全文，取到之后勾选框才可用。请求同时带上同意标志与所同意的说明版本，服务端校验版本与当前版本一致 |
| 已注册用户 | 登录后若未确认**当前版本**，先看到确认页：展示全文与「我已阅读并同意」「不同意并退出」两个按钮。确认之前其他接口都被拒绝；确认之前产生的审计事件不记录 IP |
| 不同意 | 点「不同意并退出」即登出。账号保留，下次登录仍会看到确认页；需要删除账号须联系管理员（自助删除不在本轮范围） |
| 留痕 | 账号上记录 `{version, consentedAt}`，并写一条 `privacy_consented` 审计事件 |
| 说明更新 | 隐私说明正文与版本号随代码发布。发布新版本后，所有账号（含管理员）下次使用时重新确认 |
| 管理员开的账号 | 管理员在后台创建的账号没有经过注册页，该用户首次登录时走「已注册用户」的确认流程 |

隐私说明正文草稿（三语）见 R20 §7。

#### 5.7 【R20】登录后门控

会话建立后，每次请求按账号当前状态派生「待办步骤」，顺序固定：

| 顺序 | 待办步骤 | 触发条件 | 完成条件 |
|------|---------|---------|---------|
| 1 | `privacy_consent` | 账号尚未确认当前版本隐私说明 | 调用同意接口并成功 |
| 2 | `totp_enroll` | 账号是管理员、未绑定两步验证，且服务已配置主密钥 | 绑定确认成功 |

- 服务端用全局中间件强制：还有待办步骤时，除退出、当前用户查询、两步验证状态、绑定开始与确认、隐私说明读取、同意提交这几类接口外，其余接口一律返回 403 并带待办步骤列表。
- 门控按请求实时派生，不写入会话记录。因此**存量会话不受部署影响也不会被销毁**，已登录的用户在加载新前端时会直接进入待办步骤。
- 前端以 `/me` 返回的待办列表驱动一个独立的引导页（S-01-account PageSpec §4）。

#### 5.8 注册页文案基线（v1.1 顺带登记）

主会话在 2026-11-24 修复了线上文案缺陷并已提交（`7c94678`）：注册页此前把「创建管理员账号 / 第一个注册的账号会成为管理员」当作通用注册文案。现在由 `registerCopyKeys(hasUsers)` 在两套文案间选择（`src/utils/authCopy.js`）：系统无用户时用「创建管理员账号」，否则用「创建账号」。login PageSpec v1.0 §3 所记的 `registerTitle` 取值是修复前的旧值，以 v1.1 为准。

#### 5.9 【R20】审计事件（本模块写入）

| 事件 | 触发点 | 结果与专属字段 |
|------|--------|---------------|
| `registered` | 注册成功 | success；`role` |
| `login_succeeded` | 会话建立 | success |
| `login_failed` | 口令未通过；账号已禁用 | failure；`reason` 为 `invalid_credentials` 或 `account_disabled` |
| `totp_succeeded` | 动态口令通过 | success |
| `totp_failed` | 动态口令或恢复码错误；或绑定确认时口令不匹配 | failure；`method` |
| `recovery_code_used` | 恢复码通过 | success；`remaining` |
| `totp_bound` / `totp_unbound` | 绑定确认成功 / 关闭 | success；`channel`、`rebind` |
| `privacy_consented` | 注册或确认页同意 | success；`version`、`channel` |

是否记录 IP 按 P-04 PRD §5.1 的策略执行。登录被限流（429）不写事件。

### 6. 状态与流转（T2）

本模块没有多状态业务单据。涉及的状态：

1. 账号状态：`disabled` false→true（由 D-01 用户治理修改；本模块仅在登录时消费，禁用即拒登）。规则：不能禁用自己、不能禁用最后一个管理员（在 D-01 侧强制，`server/routes/admin.js:167-176`）。
2. 准入开关状态：`env 默认 → 管理台写入（source: 'env'→'admin'）`；写入后管理值覆盖 env，直至文档被再次修改（无「清除回落 env」操作，本版本未提供）。
3. 【R20】登录流程：

```
口令步骤 ──口令错误──────────────→ 结束（401，审计 login_failed）
         ──账号已禁用────────────→ 结束（403，审计 login_failed）
         ──未启用两步验证────────→ 已建立会话
         ──已启用两步验证────────→ 二次验证步骤（预登录凭据，5 分钟）
                                      ──动态口令或恢复码正确──→ 已建立会话
                                      ──错误（15 分钟内 ≤5 次）→ 停留本步骤
                                      ──第 5 次失败或凭据过期──→ 结束（回到口令步骤）

已建立会话 → 待办 = [privacy_consent?, totp_enroll?] → 待办清空 → 正常使用
```

4. 【R20】两步验证状态：

```
未绑定 ──绑定确认成功（self / forced_enrollment）──→ 已启用
已启用 ──重新绑定──→ 已启用（新密钥、新恢复码）
已启用 ──关闭（仅普通用户）／管理员重置／服务器脚本重置──→ 未绑定
```

### 7. 业务字段（T1）

账号（users 集合）：

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| username | string | 归一后全局唯一，`^[a-z0-9_]{3,32}$` | 登录凭证 |
| passwordHash | string | bcrypt(12) | 不出域，任何响应不返回 |
| role | 'admin' \| 'user' | 首用户必为 admin | 权限判定 |
| disabled | boolean | 默认 false | 禁用即拒登 |
| createdAt | number | epoch-ms | 审计 |
| 【R20】totp | object（可选） | 见下 | 两步验证凭据；不存在即未绑定 |
| 【R20】privacy | object（可选） | `{version: string, consentedAt: Date}` | 隐私说明同意记录；不存在即从未同意 |

【R20】`totp` 子文档：

| 字段 | 类型 | 说明 |
|------|------|------|
| enabled | true | 已启用 |
| secretEnc | string | AES-256-GCM 密文，格式见 S-01 API §4.1；绝不存明文 |
| iv | string | 本次加密的 12 字节随机初始向量（base64url） |
| authTag | string | 16 字节认证标签（base64url） |
| boundAt | Date | 绑定时间 |
| lastUsedStep | number | 最近一次成功使用的时间步；防重放 |
| recoveryCodeHashes | string[] | 未使用的恢复码散列；用一个少一个 |
| pending | object（可选） | 待确认的绑定：`{secretEnc, iv, authTag, expiresAt}`；确认成功后转正并删除 |

对外用户表示 `publicUser`：仅 `{ id, username, role }`（`server/lib/authPolicy.js:42-51`），id 是其余模块的 ownerId。【R20】新增字段不进入 `publicUser`，也不进入 D-01 的用户清单响应（清单只额外返回布尔值 `totpEnabled`）。

会话（sessions 集合）：`tokenHash`（sha256）、`userId`、`createdAt`、`expiresAt`（`server/lib/session.js:30-40`）。

注册开关（app_settings 单例 `_id='registration'`）：`registrationOpen`（boolean）、`updatedAt`（epoch-ms）、`updatedBy`（管理员用户名）（`server/routes/admin.js:84-88`）。单例字符串 _id 非二十四位 hex，天然唯一且备份往返不变形（`server/lib/authPolicy.js:1-4`）。

【R20】预登录凭据（进程内存，不落库）：`ticketHash`（sha256）→ `{userId, expiresAt}`。

### 9. 异常与降级（N2）

| 场景 | 行为 |
|------|------|
| 注册关闭时提交注册 | 403「Registration is closed」，注册限额仍计数 |
| 数据库异常 | 5xx + 服务端 message，前端展示错误提示 |

| 【R20】前端拿到的 `/me` 响应没有 `pending` 字段 | 按「无待办」处理。用于新前端对接旧 API 的发布窗口 |

### 10. 非功能性要求（N1）

- 用户量级：社团规模（数十至数百账号），单文档读写无性能压力；`registrationState()` 每请求仅一次 `countDocuments` 加一次单例读取（`server/routes/auth.js:40-45`）。
- 口令计算 bcrypt cost=12，登录与注册 QPS 低，可接受。
- 会话 TTL 30 天，滑动场景由前端重新登录覆盖。
- 安全：口令不出域、令牌只存散列、统一 401 不泄露账号存在性、登录页防开放重定向。
- 【R20】两步验证校验是几次 HMAC-SHA1 计算，微秒级；每次请求派生待办步骤不增加数据库读取（复用鉴权时已加载的账号文档）。
- 【R20】前端体积：Lighthouse CI 审计的 `/`，在无 API 的预览环境下未登录会落到登录页（依据见 R20 §9.6）。二次验证步骤与隐私说明弹窗必须放在按需加载的独立代码块里，不进入登录页首屏。

### 11. 历史与追溯（N4）

- 账号存 `createdAt`；会话不审计；开关单例存 `updatedAt`、`updatedBy`（最后一次修改者用户名）。
- v1.0 时本模块没有操作日志。自 v1.1 起，§5.9 列出的登录类与两步验证类事件写入审计日志（P-04），留存 184 天。
